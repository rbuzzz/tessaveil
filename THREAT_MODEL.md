## English

<!-- en:boundary -->
### Scope and trust boundary

This is the public threat contract for a proposed offline backup table, not a usable vault or an audited security product. Protections below are design requirements unless a linked research report explicitly measures them. Do not use this repository to protect real funds or enter real recovery material into its probes.

Tessaveil briefly sees the current word and column while placing one word. It cannot defeat a compromised OS. It does not validate complete phrases, reconstruct their order, check mnemonic checksums, derive keys or addresses, or verify balances. It does not replace a separate cold backup or trusted hardware-wallet process. A catalogue profile's `verified` status concerns researched compatibility; it does not verify the user's phrase. "Verified by me" is the user's independent confirmation through the original trusted wallet or official hardware-wallet backup check, not a Tessaveil cryptographic check.

The intended encrypted payload holds decoy tables, names, profile/dictionary snapshots, settings and user verification flags. It must not store the order key or its verifier/pattern/hint, target cells, transient Spin inputs as separate fields, a complete reconstructed phrase, successful-row markers, input history or prior versions. A placed word still exists among the table's words; absence of target metadata does not make it absent from the table. External wallet passphrases remain external secrets and must not be stored in table metadata.

A sheet password prevents accidental UI edits after unlock. It is not a second cryptographic boundary once the master password or decrypted payload is compromised. Auto-lock, masked input, immediate clearing and screen covering reduce incidental exposure only. Clearing is best effort: immutable UI strings, malicious IME buffers, process memory, swap and crash dumps may retain input. A hostile OS, keylogger or screen recorder can capture words and columns as they are entered or read.

### Spin and observation

Valid and invalid input follow the same UI process: no explicit validity result, no success signal, no target-column output and no saved metadata signal. The entire current row is regenerated; an allowed word is placed in the transient column, while invalid input leaves an ordinary random word there. This is a control-state contract, not a claim that visible data are indistinguishable: visible row contents may differ, and valid input visibly places the requested word.

Repeated observations and attempts can correlate invariant words across rows, narrow candidates or expose an order-key pattern. A neutral repeat warning must not disclose previous validity. Spin is limited visual masking, not a proof against observation, repeated attempts, screen recording or a compromised device. Neither a uniform animation nor clearing input removes information already observed.

### Redundancy, edits and comparison

Identical redundant copies of one unchanged table do not add a new table-comparison signal. Extra copies still increase exposure locations. Re-encrypting the same unchanged table may change file bytes without introducing a different table. Different saved tables for the same original phrase are the relevant comparison risk, including manual copies, replacement sheets and interrupted-save remnants; comparison requires access to their decrypted contents or equivalent observations.

If the true word is retained while decoys change, intersections across a row's versions may narrow to that word. Full row or table re-randomization does not remove cross-version intersection risk. A row update is not a solution to this risk. There is no cosmetic reshuffle, no "safe refresh" promise and no automatic phrase-preserving migration.

Warn before editing a previously saved row and before creating a replacement sheet: old files may still exist and become readable after later password disclosure. Absence of built-in history does not prevent manual backups, filesystem/cloud versions or deleted-data recovery. Best-effort cleanup is not secure erasure. Changing the master password re-encrypts the current image but does not revoke old copies or their old passwords. Redundancy guidance must never imply that retaining changed versions is equally safe or instruct users to destroy their only usable recovery copy.

<!-- en:dictionary-contract -->
### Custom dictionary changes

Every existing sheet owns an immutable dictionary snapshot inside the encrypted vault. A revised list creates a new unverified sheet; the user must fill and independently verify it again. "Verified by me" never transfers. Table cells, row state and protection state do not transfer. The old sheet stays unchanged until explicit deletion. The new list must not silently replace the populated sheet's snapshot or regenerate its rows.

There is no automatic phrase-preserving migration: Tessaveil neither knows nor reconstructs the complete true phrase and column sequence. The new profile remains "Custom — compatibility not verified." Creating another table from the same phrase triggers the comparison warning even when the dictionary change is legitimate. Deleting the old sheet later cannot guarantee removal of prior copies.

### Temporary images, rollback and storage evidence

The proposed temporary file contains a clear technical header plus authenticated ciphertext, with no plaintext payload. Technical fields include format/KDF identifiers, bounded KDF parameters, salt, nonces, wrapped key and parsing lengths; names, settings, dictionaries and tables belong inside encrypted payload. This describes the application's write contract, not a guarantee against OS swap or dumps. A complete temporary image may preserve a comparison-useful version after password disclosure. Partial or unauthenticated images must not appear as a valid empty vault. Cleanup is best effort.

There is no rollback detection without trusted external monotonic state. Authentication alone cannot distinguish a current image from an older authentic one. No password attempt limit or self-destruction policy prevents offline guessing of copies.

Test local NTFS, removable NTFS and removable exFAT separately for the exact device, Windows version and replacement API. The [local research matrix](reports/spikes/filesystem-matrix.md) observed old-or-new authenticated images at specified process interruption boundaries on a development volume. It does not prove power-loss durability, atomicity inside the system call, all replacement error recovery, clean-machine readiness or removable-media behavior. Never silently fall back to in-place overwrite or delete-before-rename.

FAT32, network shares, cloud-synchronized folders and unverified filesystems carry no atomicity promise. The intended policy is read-only or Save As to a verified target. This is a future product requirement; no current product support is implied. [ADR 0003](docs/adr/0003-filesystem-replace.md) scopes the existing evidence and the remaining blockers.

<!-- en:gates -->
### Evidence and open gates

Research completion does not grant release permission. This matrix documents intended controls, not implemented product guarantees. Windows release: NO-GO. Format/KDF freeze: NO-GO. Physical mobile evidence: blocked. Removable-media guarantees: NO-GO. Desktop selection remains provisional. Host crypto tests, catalogue completeness and this document cannot clear physical, signing, independent review or release gates.

See the [foundation specification](docs/superpowers/specs/2026-09-29-tessaveil-foundation-windows-v1-design.md), [research specification](docs/superpowers/specs/2026-09-29-tessaveil-registry-threat-model-design.md), [desktop ADR](docs/adr/0001-desktop-stack.md), [format/KDF ADR](docs/adr/0002-kdf-envelope-bounds.md) and [equipment blockers](reports/spikes/equipment-availability.md). The [catalogue](docs/catalog.md) separates terminal research coverage from release blockers. Changes to the threat boundary or copy require review in both languages; automated wording checks are not a security audit.

### Область действия и граница доверия

Это публичная модель угроз для предлагаемой офлайн-таблицы резервного хранения, а не рабочее хранилище или прошедший аудит продукт. Описанная защита — требования к будущему продукту, если связанный исследовательский отчёт прямо не подтверждает конкретное измерение. Не защищайте этим репозиторием реальные средства и не вводите настоящие секреты в прототипы.

Tessaveil кратковременно видит текущее слово и столбец при размещении одного слова. Он не может противостоять скомпрометированной ОС. Он не проверяет целые фразы, не восстанавливает их порядок, не проверяет контрольную сумму мнемоники, не выводит ключи и адреса и не проверяет баланс. Он не заменяет отдельную холодную резервную копию или доверенную процедуру аппаратного кошелька. Статус профиля `verified` относится к исследованной совместимости, а не к проверке фразы пользователя. "Verified by me" — подтверждение самого пользователя через исходный доверенный кошелёк или официальную проверку резервной копии аппаратного кошелька, а не криптографическая проверка Tessaveil.

В зашифрованной полезной нагрузке предполагается хранить таблицы с ложными словами, названия, снимки профилей/словарей, настройки и пользовательские отметки проверки. Нельзя сохранять ключ порядка, его проверочный признак/шаблон/подсказку, целевые ячейки, временный ввод Spin отдельными полями, целую восстановленную фразу, отметки успешных строк, историю ввода и предыдущие версии. Размещённое слово остаётся среди слов таблицы; отсутствие метаданных цели не исключает слово из таблицы. Дополнительные парольные фразы кошельков остаются внешними секретами и не входят в метаданные таблицы.

Пароль листа препятствует случайным правкам в UI после разблокировки. Он не является вторым криптографическим барьером при раскрытии мастер-пароля или расшифрованной полезной нагрузки. Автоблокировка, маскировка ввода, немедленная очистка и закрытие экрана лишь уменьшают случайное раскрытие. Очистка выполняется по мере возможности: неизменяемые строки UI, буферы вредоносного IME, память процесса, подкачка и аварийные дампы могут сохранять ввод. Враждебная ОС, кейлоггер или запись экрана способны захватить слова и столбцы при вводе и чтении.

### Spin и наблюдение

Допустимый и недопустимый ввод проходят одинаковый процесс в UI: нет явного результата допустимости, нет сигнала успеха, нет вывода целевого столбца и нет сохранённого признака результата. Вся текущая строка создаётся заново; допустимое слово помещается во временно выбранный столбец, а при недопустимом вводе там остаётся обычное случайное слово. Это требование к состояниям управления, а не обещание неразличимости видимых данных: видимое содержимое строк может различаться, и допустимый ввод явно помещает запрошенное слово.

Повторные наблюдения и попытки позволяют сопоставлять неизменные слова между строками, сужать кандидатов или раскрывать шаблон ключа порядка. Нейтральное предупреждение о повторе не должно раскрывать допустимость прошлого ввода. Spin — ограниченная визуальная маскировка, не доказательство защиты от наблюдения, повторных попыток, записи экрана или компрометации устройства. Одинаковая анимация и очистка ввода не удаляют уже увиденное.

### Резервирование, правки и сравнение

Идентичные резервные копии одной неизменённой таблицы не добавляют нового сигнала сравнения таблиц. Дополнительные копии всё равно увеличивают число мест возможного раскрытия. Повторное шифрование той же неизменённой таблицы может менять байты файла без создания другой таблицы. Риск сравнения создают разные сохранённые таблицы одной исходной фразы, включая ручные копии, заменяющие листы и остатки прерванного сохранения; для сравнения нужны расшифрованные данные или эквивалентные наблюдения.

Если настоящее слово остаётся, а ложные меняются, пересечения версий строки могут сузиться до этого слова. Полная повторная рандомизация строки или таблицы не устраняет риск пересечения разных версий. Обновление строки не решает эту проблему. Косметической перетасовки нет; нет обещания «безопасного обновления» и автоматического переноса с сохранением фразы.

Предупреждайте перед изменением ранее сохранённой строки и перед созданием заменяющего листа: старые файлы могут сохраниться и стать читаемыми после раскрытия пароля. Отсутствие встроенной истории не исключает ручные копии, версии файловой системы/облака и восстановление удалённых данных. Очистка по мере возможности не является гарантированным стиранием. Смена мастер-пароля заново шифрует текущий образ, но не отзывает старые копии или их старые пароли. Рекомендации по резервированию не должны приравнивать безопасность изменённых версий к идентичным копиям или предлагать уничтожить единственную пригодную копию восстановления.

### Изменения пользовательского словаря

Каждый существующий лист имеет неизменяемый снимок словаря внутри зашифрованного хранилища. Изменённый список создаёт новый непроверенный лист; пользователь должен заполнить и независимо проверить его заново. "Verified by me" никогда не переносится. Ячейки таблицы, состояние строк и защиты не переносятся. Старый лист остаётся неизменным до явного удаления. Новый список не должен скрыто заменять снимок заполненного листа или перегенерировать его строки.

Автоматического переноса с сохранением фразы нет: Tessaveil не знает и не восстанавливает полную настоящую фразу и последовательность столбцов. Новый профиль остаётся «Пользовательский — совместимость не проверена». Создание другой таблицы той же фразы требует предупреждения о сравнении даже при обоснованной смене словаря. Последующее удаление старого листа не гарантирует исчезновение прежних копий.

### Временные образы, откат и доказательства по носителям

Предлагаемый временный файл содержит открытый технический заголовок и аутентифицированный шифротекст, без открытого содержимого полезной нагрузки. Технические поля включают идентификаторы формата/KDF, ограниченные параметры KDF, соль, nonce, обёрнутый ключ и длины для разбора; названия, настройки, словари и таблицы находятся внутри зашифрованной полезной нагрузки. Это требование к записи приложения, не гарантия против подкачки или дампов ОС. Полный временный образ может сохранить полезную для сравнения версию после раскрытия пароля. Частичные или неаутентифицированные образы не должны выглядеть как корректное пустое хранилище. Очистка выполняется по мере возможности.

Обнаружение отката не обещается без доверенного внешнего монотонного состояния. Одна аутентификация не отличает текущий образ от старого аутентичного. Ограничение попыток пароля или самоуничтожение не предотвращает офлайн-подбор копий.

Локальный NTFS, съёмный NTFS и съёмный exFAT проверяются отдельно для конкретного устройства, версии Windows и API замены. [Локальная исследовательская матрица](reports/spikes/filesystem-matrix.md) показала сохранение старого либо нового аутентифицированного образа в указанных точках прерывания процесса на рабочем томе разработки. Она не доказывает сохранность при потере питания, атомарность внутри системного вызова, обработку всех ошибок замены, готовность чистой системы или поведение съёмных носителей. Нельзя скрыто переходить к записи поверх файла или удалению перед переименованием.

FAT32, сетевые ресурсы, папки облачной синхронизации и непроверенные файловые системы не получают обещания атомарности. Предусмотрены только чтение или Save As на проверенный носитель. Это требование к будущему продукту, а не существующая поддержка. [ADR 0003](docs/adr/0003-filesystem-replace.md) ограничивает применимость имеющихся доказательств и перечисляет блокеры.
