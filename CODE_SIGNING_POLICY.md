# Code-signing and release policy

Policy review: 2026-09-29 UTC. The [official Foundation conditions](https://signpath.org/terms.html) and [application page](https://signpath.org/apply.html) were checked; retrieval fingerprints and component-review rules are in [licensing.md](docs/research/licensing.md). Recheck before applying and releasing. No Foundation application, acceptance, certificate or integrated signing workflow is claimed at this research stage.

The first functional candidate, `v0.1.0-rc.1`, may be published as an **unsigned pre-release** because SignPath Foundation requires an already released and documented open-source project. It must carry a SHA-256 checksum, GitHub artifact provenance tied to the exact source commit, an SBOM, successful CI, test and clean-machine verification summaries, and conspicuous unsigned labeling. It is not a stable release.

The preferred later path is an owner application to SignPath Foundation. All team members must use MFA for both repository and SignPath access. Before applying, the owner assigns named author, reviewer and approver roles and publishes the required privacy and signing-policy information on the home and release pages. Required provider acknowledgments are published only once the service is actually provided. Separate authorized reviewers assess changes and an authorized approver manually approves release signing; the build must originate from the protected repository workflow and verified source. Signing requests must use SignPath's trusted-build/origin-verification flow. No contributor may sign an unreviewed local binary as a project release.

If accepted, the certificate belongs to SignPath Foundation and Windows will display **SignPath Foundation** as publisher, not Tessaveil. Acceptance and SmartScreen reputation are not guaranteed. After integration, publish a signed subsequent RC, then verify the exact signed artifact on supported clean Windows systems before any stable release.

If SignPath declines or delays the project, unsigned RCs are never stable releases. Stable publication stops pending an explicit owner decision to remedy and reapply, approve a separately funded CA certificate, or revise the release criteria. No certificate purchase or unsigned-stable exception is implicit.

Under the current criteria, stable release requires external Foundation acceptance, completed integration, a signed subsequent RC and successful checks of that exact signed artifact. Component `allowed`/`compatible` decisions do not satisfy this application-level gate. An alternative signing provider or separately approved paid CA path requires an owner decision and its own external acceptance and artifact checks before release. An explicit proposal to change acceptance criteria is not itself permission to relabel an unsigned RC as stable.
